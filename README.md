Сырые данные (`train.parquet`, `benchmark_items.parquet`, `benchmark_queries.parquet`) —
по ссылке из [`data/README.md`](data/README.md), положить в `data/`.

## Данные и признаки

- `data/train.parquet` — история поиска (запрос + контекст + выбранный `item_id`).
  Используется как для кандидатогенерации,
  так и для обучения ранкера.


Поля объявления: заголовок, описание, параметры (из текста вида
`label value label value...` достаю value), координаты и
`location_id`, цена, рейтинг, число отзывов, флаги из параметров, `item_microcat_id`.

Почему именно эти признаки:
- **Текст** - лексика и семантика
- **Гео** - локальная близость самый сильный сигнал, даже в соло.
- **Структурированные параметры** - матчинг при условии существования 
- **Популярность** - человеческое доверие.
- **Подкатегория объявления** - в запросе поля подкатегории нет, поэтому
  она предсказывается по похожим историческим запросам и lookup, и используется как дополнительный признак для ранкера.

Каналы кандидатогенерации (каждый отвечает за поиск релевантных ему пулов):
- BM25 по тексту объявления;
- взвешенный BM25
- локальный (гео) BM25
- эмбеддинги
- char n-gram TF-IDF 
- lookup по истории
- география.

## Модели и алгоритмы

Двухэтапная схема кандидатогенерация => ранжирование:

1. Каждый канал возвращает широкий пул кандидатов.
2. Кандидаты объединяются в общий пул, для каждого считается единая эвристическая оценка (нормированный BM25 + гео-бонус + бонус за совпадение категории + бонус популярности)
3. Из широкого пула отбирается top-500 - набор кандидатов на ранжирование.
3. **CatBoostRanker** (`PairLogit`, глубина 6, `learning_rate=0.08`, early stopping 40 итераций) переранжирует пул по ~64 признакам: сигналы по каждому каналу, гео, категория, числа объявления.
4. Ответ - взвешенный RRF между ранжированием
   CatBoost, эвристическим пулом и строгим геоканалом: веса отдельно на proxy-оценке по бенчмарк-каталогу.

Почему `CatBoostRanker`/`PairLogit`: попарная функция потерь полностью соответствует задаче - релевантное объявление должно оказаться выше нерелевантного в
топ-50.

- Юзал библиотеки и модели: `bm25s`, `catboost`, `sentence-transformers` + `intfloat/multilingual-e5-base`, `scikit-learn` (tf-idf, BallTree), `pandas`/`numpy`. 
- Эмбеддинги каталога объявлений (train и bench) заранее посчитал на kaggle, а при запуске решения эмбеддинги запросов считаются той же моделью локально.

## Как проверялось качество

- реализация Recall@50
- разбиение train/val без лика: сплит по полному поисковому контексту, а не по отдельному объявлению, чтобы повторные одинаковые запросы не утекали.
- Сравнение вариантов пула кандидатов (`PoolExperiment.compare()`) на фиксированной выборке контекстов перед выбором финальной схемы - таблица
  метрик по каждому каналу и варианту сохраняется и версионируется.
- benchmark-proxy проверка: реальные `benchmark_queries`, но релевантность учитывается только там, где нужный `item_id` есть в `benchmark_items`; 70% контекстов используются для выбора финальной политики смешивания, 30% — как честный holdout.
- Раздельно отслеживались warm (запрос встречался в истории) и cold (новый) контексты: доля новых текстов в реальном бенчмарке заметно выше,
  чем в локальном val-сплите, поэтому финальная политика выбиралась по метрике, взвешенной в пользу cold-контекстов - иначе легко переобучиться под локальное распределение.
- feature importance (`PredictionValuesChange`): гео-дистанция и гео-бонус - доминирующие признаки, что подтверждает локальность.

## Найденные ошибки и что с ними сделано

- **Наивное объединение каналов.**
Конкатенация списков кандидатов от
  разных каналов с обрезкой до 50 приводила к тому, что первый канал вытеснял вклад остальных - итоговый recall долго ~совпадал с recall первого канала. \
Исправил переходом на схему «общий
  пул (500) → единый скоринг → обрезка до 50 в конце».
- **Добавление контекста параметров запроса к запросу перед постройкой эмбеда**\
Эмбединг строится на основе запроса и контекста параметров запроса, чтобы учесть влияние параметров на эмбединг. Но медианная длина запроса=2, и контекст параметров(к примеру, вид услуги ремонтные работы) размывал конкретный запрос на более общий пул запросов. Качество эмбедов ухудшилось на консистентном экспе. Вернулся к простому эмбеду без параметров запроса
- **Рассинхрон позиций гео-индекса.** \
BallTree по координатам отбрасывал
  несколько объявлений без координат, из-за чего позиции кандидатов переставали
  совпадать с индексацией BM25-корпуса.\
Исправлено явным маппингом
  `item_id<=>позиция`
- **Память при построении char tf-idf.**\
Матрица изначально строилась в памяти
  как плотная - исправил обрезкой длины
  текста, порогом встречаемости, ограничением размера словаря и sparse top-k извлечением кандидатов
- **Несовпадение распределений локальной валидации и бенчмарка.** \
Доля новых текстов в бенчмарке заметно выше, чем в локальном val-сплите. Обнаружено сравнением статистик пересечения текстов.
Исправлено cold/warm-взвешенной proxy-оценкой при выборе финальной политики
